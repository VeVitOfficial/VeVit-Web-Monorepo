# Release 0 · Task 0.2 — bezpečný checkout snapshot

## Rozsah

Původní `api/create-checkout.php` prováděl N+1 dotazy, přepočítával peníze pomocí
`float`, vytvořil objednávku i download token před platbou a ihned volal Stripe.
Klient posílal pouze `product_id` a množství, ale endpoint nevynucoval úplnou
serverovou validaci a digitální položky se při následném insertu načítaly bez
kontroly aktivního stavu.

Task 0.2 zavádí `CheckoutService` a ukončuje přímé vytvoření Stripe checkout
session. Endpoint nyní vytvoří pouze bezpečný, 30 minut platný snapshot v
oddělené neveřejné tabulce `store_checkout_snapshots` — nevytváří ani
`store_orders` řádek. Tím nemůže stará success stránka podle čísla objednávky
zpřístupnit předběžný checkout. Platební krok je úmyslně odložen do navazujícího
tasku; zákazníkovi se nevydává URL Stripe, download token ani cesta k digitálnímu
souboru.

Endpoint přijímá pouze `POST` JSON do 32 KiB, vyžaduje scoped CSRF token a
idempotency key. Klientské položky mohou kvůli kompatibilitě obsahovat stará
zobrazovací/přícenová pole, ale server je zahodí a událost zapíše bez hodnot do
bezpečnostního logu.

Vytváření snapshotů je navíc atomicky omezeno v PostgreSQL podle session
(5 požadavků/min) a zdrojové IP (30 požadavků/min). Identifikátory rate-limit
bucketů se ukládají pouze jako SHA-256 hash. `X-Forwarded-For` se bez
ověřeného proxy kontraktu záměrně nepoužívá.

## Snapshot

`store_checkout_snapshots.snapshot_data` obsahuje serverem ověřené položky: produkt,
volitelně budoucí variantu (v této verzi vždy `null`), SKU, název, typ,
množství, částky v haléřích, měnu, stav skladu, backorder, mezisoučet, dopravu,
celkem, okamžik a expiraci. Budoucí potvrzená objednávka z tohoto snapshotu
teprve vytvoří `store_orders` a `store_order_items`.

Snapshot je uložen na serveru, identifikován 128bitovým náhodným `public_id` a
má SHA-256 hash uložený v samostatném sloupci. Repository hash při opakovaném
idempotentním požadavku ověřuje. Grant pro hosta vzniká z 256bitového náhodného
zdroje, do databáze se zapisuje jen SHA-256 hash a syrová hodnota zůstává pouze
v aktuální PHP session. V Tasku 0.2 zatím neexistuje endpoint, který by podle
`public_id` snapshot nebo objednávku zpřístupnil.

## Souběh a změny dat

Stejná kombinace scope (uživatel nebo session) a idempotency key je v PostgreSQL
serializována transakčním advisory lockem a chráněna unikátním indexem. Druhý
požadavek vrací existující snapshot pouze ve stejném scope; expirovaný snapshot
se označí jako `expired` a bezpečně se vytvoří nový.

Produkty se v jediné transakci načtou pomocí `FOR UPDATE`. Sklad se v tomto
tasku nerezervuje ani neodečítá. Proto dva zákazníci mohou vytvořit snapshot pro
poslední kus, ale nesmí tím vzniknout platba: budoucí vytvoření platební session
a webhook znovu ověří snapshot a provedou jediný transakční skladový pohyb.
Fyzický produkt s `stock = NULL` se bez výslovného `allow_backorder` bezpečně
odmítne. Cena, aktivita produktu nebo sklad se po snapshotu mohou změnit;
navazující platební task musí kontrolovat `snapshot_hash`, expiraci a aktuální
prodejnost ještě před zahájením platby.

## Migrace a rollback

`migrations/202607290001_checkout_snapshot_up.sql` je pouze aditivní: přidává
prodejnost, měnu a backorder produktu, samostatnou tabulku neveřejných
checkout snapshotů a hashované rate-limit buckety. Nemění existující produkty,
objednávky ani uživatele.

Rollback SQL je určen výhradně před vznikem reálného snapshotu. Po vytvoření
objednávek je bezpečný postup obnova ověřené databázové zálohy, ne odstranění
auditních sloupců.

## Známé limity

- Varianty zatím v aktuálním datovém modelu neexistují; požadavek s `variant_id`
  je bezpečně odmítnut.
- Digitální vazba se ověřuje proti `APP_STORAGE_PATH`; produkt bez existujícího
  souboru uvnitř této neveřejné cesty se odmítne.
- Platba Stripe, finální autorizace snapshotu, rezervace/odečet skladu, IDOR
  objednávek a digitální download autorizace patří do následujících tasků.
- Integrační PostgreSQL test vyžaduje oddělenou testovací databázi; finální
  stabilizační sada jej spouští v izolovaném PostgreSQL 16 prostředí.
