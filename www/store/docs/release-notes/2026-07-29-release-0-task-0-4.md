# Release 0 · Task 0.4 — transakční objednávky a platby

## Bezpečný tok

1. `api/create-checkout.php` vytvoří krátkodobý serverový snapshot z ID a
   množství; cenu, měnu, sklad a digitální vazbu načte z PostgreSQL.
2. `PaymentOrderService` v transakci zamkne snapshot, autorizuje vlastníka nebo
   guest grant, zkontroluje expiraci a SHA-256 integritu, hromadně znovu načte
   a zamkne produkty, přesně přepočte ceny bez `float` a vytvoří jedinou
   historickou objednávku. Unikátní index na `checkout_snapshot_id` a row lock
   chrání souběh.
3. `StripeCheckoutService` používá pouze data objednávky a kanonickou `APP_URL`.
   Stripe idempotency key je serverově namespacovaný podle náhodného public ID
   a čísla pokusu. Opakovaný request vrátí uloženou session; expirovaná session
   zvýší číslo pokusu. Metadata obsahují jen verzi schématu a public ID.
4. Redirecty `success.php` a `cancel.php` stav platby nemění. Success pouze
   autorizovaně čte databázový stav.
5. `api/webhook.php` pracuje s raw body a ověřuje Stripe HMAC podpis. Jediný
   autoritativní event je synchronně zaplacený `checkout.session.completed`;
   Checkout Session je proto v Release 0 omezena na kartu.
6. `StripePaymentProcessor` v jedné transakci vloží/uzamkne unikátní event
   ledger, uzamkne objednávku, přesně ověří session, Payment Intent, částku,
   měnu, live/test režim a volitelný účet. Teprve potom předem ověří všechny
   položky, vloží unikátní skladové pohyby a digitální entitlementy a označí
   objednávku jako zaplacenou.

## Stavy

- Platba: `pending_checkout → awaiting_payment → paid`; povoleny jsou též
  explicitní `failed`, `cancelled`, `refunded` a `manual_review`.
- Fulfilment: `pending → ready → processing → fulfilled`, případně
  `manual_review`.
- Opožděný failure/expiry event je pouze auditovaný a nikdy nevrátí `paid`
  objednávku zpět.
- Duplicitní finální přechod je no-op.

Pokud je po potvrzené platbě nedostatek skladu nebo neplatný digitální obsah,
nevznikne žádný částečný movement ani entitlement. Důkaz platby se zachová,
objednávka dostane `payment_status=paid` a
`fulfillment_status=manual_review`. Další Stripe retry ji automaticky
nefulfilluje; vyžaduje vědomé interní řešení.

## Digitální obsah

`store_download_entitlements` je trvalé oprávnění vznikající právě jednou na
zaplacený digitální `order_item`. Až autorizovaný POST uživatele z entitlementu
vydá pětiminutový jednorázový bearer grant v `store_download_grants`; raw token
není v databázi ani webhooku. Deaktivace před potvrzením platby způsobí
`manual_review` a entitlement nevznikne. Již vytvořený entitlement lze
revokovat; deaktivace katalogového produktu sama historický nákup neruší.

## Nasazení a rollback

1. Vypněte payment endpoint nebo použijte servisní okno.
2. Vytvořte a ověřte PostgreSQL backup.
3. Spusťte `202607290003_preflight_report.sql`; vyřešte duplicity.
4. Spusťte migraci `202607290003_payments_and_inventory_up.sql` s
   `ON_ERROR_STOP=1`.
5. Doplňte Stripe test konfiguraci, ověřte webhook endpoint a spusťte smoke
   platbu v test mode.
6. Teprve potom povolte produkční klíče.

Před první novou platbou lze použít down migraci. Po první platbě rollback
znamená atomickou obnovu aplikace i databáze z ověřené zálohy; samostatné
odstranění ledgeru by zničilo auditní stopu.

## Ověření

`tests/run-task-0-4.sh` obsahuje unit testy a skutečný PostgreSQL test s
`FOR UPDATE`, unikátními indexy, dvěma procesy, posledním kusem a injektovanými
chybami po prvním movementu i při entitlementu. Izolované prostředí je v
`tests/docker/php-postgres/Dockerfile`; CI workflow používá PostgreSQL 16 service.

Závěrečná stabilizace rovněž ověřuje opakované migrace i jejich bezpečný
rollback před první transakcí, PostgreSQL rate limiting checkout snapshotů a
explicitní allowlist veřejných produktových API bez `download_file` a
`stripe_price_id`. Produkční nasazení zůstává blokované závěrečným Taskem 0.5.
