# Release 0 · Task 0.3 — autorizace objednávek a digitální downloady

## Původní zranitelnost

`success.php?order=<order_number>` načítal objednávku pouze podle sekvenčního
čísla, zobrazil jméno, e-mail, položky a raw download tokeny. Odkaz
`download.php?token=<token>` token přijímal v URL, neověřoval vlastníka
objednávky a skládal cestu k souboru z webového rootu. Raw token vznikal již při
vytvoření nezaplacené objednávky.

## Nový model

Objednávka je zobrazena jen přes náhodný `public_id` a centralizovanou kontrolu:
vlastník ze serverové session, guest grant uložený pouze jako SHA-256 hash nebo
administrátor. Samotné číslo objednávky ani public ID nikdy nestačí. Neznámý i
neautorizovaný přístup vrací shodnou 404 odpověď. Success stránka používá
`Cache-Control: no-store, private`, `Pragma: no-cache` a `Referrer-Policy:
no-referrer`; neobsahuje raw token ani storage cestu.

Digitální oprávnění se ukládá v `store_download_grants`. Krátkodobý jednorázový
token se vydá až po autorizovaném POSTu a ověření zaplacené digitální položky.
Databáze ukládá pouze hash tokenu. `download.php` přijímá POST, kontroluje CSRF,
grant, stav objednávky, položku, expiraci, revokaci, limit a bezpečnou canonical
cestu pod `APP_STORAGE_PATH`; počet stažení navyšuje atomickým SQL predikátem.

Pravidlo pro deaktivovaný produkt: nelze jej nově koupit. Výchozí grant přístup
k neaktivnímu obsahu nemá; autorizované vydání grantu pro již zaplacenou položku
však tuto výjimku explicitně zapisuje jako `allow_inactive_access=true` včetně
auditní metadata. Refundace nebo právní zásah může volat
`DownloadService::revokeOrderGrants()`.

## Migrace starých tokenů

1. Předem spusťte pouze report:

```bash
psql "$DB_DSN" -f migrations/202607290002_legacy_download_token_report.sql
```

2. Vytvořte ověřenou zálohu a spusťte migraci `202607290002..._up.sql`.
3. Migrace nulují původní raw tokeny, ale nemažou objednávky ani historické
   počitadlo stažení. Nejasné, nezaplacené a staré guest objednávky se automaticky
   neodemykají.
4. Nový grant lze vytvořit jen následným bezpečným procesem pro ověřeného
   zákazníka; před reálnými Stripe webhooky není automatické znovuvydání možné.

Historické objednávky nemají automatický backfill `public_id` ani guest grantu:
jejich veřejná success stránka proto po nasazení vrací 404. Je to vědomý
fail-closed dopad; zůstávají dostupné administrátorům. Bezpečný zákaznický
recovery tok vyžaduje pozdější ověřený e-mailový nebo účetní proces, nikoli grant
odvozený z čísla objednávky.

Rollback před prvním novým grantem je v `202607290002..._down.sql`. Po vydání
grantů obnovujte databázi pouze z ověřené zálohy.
